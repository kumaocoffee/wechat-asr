# 长音频验证与原生协议调查

2026-10-14，在已登录的微信 4.1.13.65 上，去掉桥接器的 15 秒校验和 FFmpeg `-t 15.02` 后，单包提交仍然失败。改为同一原生会话内分包提交后，42.97 秒和 75.32 秒的合成语音均返回结尾内容；75.32 秒 WAV/MP3 的 HTTP SDK 调用也完成验证。

## 实测区别

| 提交方式 | 合成音频时长 | 结果 |
| --- | ---: | --- |
| 单包 | 6.28 / 10 秒 | 正常返回文字 |
| 单包 | 20 / 30 / 35 / 36 / 40 / 42.97 秒 | 最终响应文字为空 |
| 单包 | 75.32 秒 | 原生 `recognition_error`，`code=100`、`detail=0` |
| 按 Opus 帧边界分包 | 42.97 秒 | 识别出第 36 秒开始的独立结尾 |
| 按 Opus 帧边界分包 | 75.32 秒 | 识别出第 68.344 秒开始的独立结尾 |

75.32 秒样本包含不同句子的连续合成语音，开头为“春天的花园”，中间为“蓝色的火车”，独立结尾为“紫色的望远镜”。核验结尾可以避免把请求成功或只识别开头误认为长音频支持。

## 原生代码和格式证据

所有 RVA 仅适用于 README 中指纹一致的 DLL：

- `0x615FE50` 从编码器取出已编码数据和帧数。反汇编中 `0x615FF05` 写入 `0x14`，对应每帧 20 毫秒，`0x615FF0B` 读取帧数。
- 编码器输出以 `#!OPUS_RAW_V1` 开头，头部共 16 字节；后续每帧为 2 字节小端长度和对应的 Opus 数据。6.28 秒样本解析得到 314 帧，解析终点与 10,136 字节输出完全一致。
- iLink 策略虚表位于 `0x991DE58`，发送入口为 `0x6EA2090`。发送参数包含包序号、结束标志和 codec；入口分别保留第三、第四参数，并在 `0x6EA22C0`、`0x6EA2351` 写入请求字段。
- `0x6905510` 处理返回到识别会话的响应。单包长音频能够到达响应路径，因此不能把失败简单归因于桥接器的等待超时。

当前查看的编码、发送和响应函数中，没有定位到明确的 15 秒或 35 秒总时长比较。单包失败的精确阈值以及错误码 100 的完整语义尚未恢复，不能据此宣称微信完全没有限制。相同长音频分包成功，足以证明这条接口支持超过 35 秒的内容，也说明整包提交方式是本次失败的重要因素。

## 当前实现

`agent.js` 完整编码一次，验证格式和帧数，按每包最多 250 帧（5 秒）切分。流头仅留在第一包，包序号从 1 递增，仅最后一包置结束标志。所有包属于同一原生识别会话，保持编码器状态并保留每一帧；不按 15 秒拆成互相独立的转写请求。

Python 不再限制音频总时长，也不截取 FFmpeg 输入。仍保留 25 MiB 上传限制、20 秒解码等待、60 秒原生结果等待及单请求准入。已验证的 75.32 秒不代表任意时长都能成功。

## 复现

服务运行时执行：

```powershell
.\env\python.exe tests\verify_long.py
```

此脚本复用仓库已有的合成 fixtures，在第 37.68 秒后放入不同的结尾语音，分别测试 WAV 和 MP3，并校验返回时长、结尾文字、会话清理及服务健康状态。无需新增 TTS 依赖或个人录音。

本机额外的 75.32 秒语音用 Windows Huihui 合成；原始音频、反汇编输出和带事件的诊断报告仅保存在被 Git 忽略的 `.runtime/`。未修改微信 DLL，也未提交微信二进制或运行 PID。
